# ET S2 Worker 引导阶段诊断

## 基线与根因

从本仓 0f3b690 继续。实际 Worker 在进入原异常捕获边界前加载 provider 传输和 HTML 提取依赖。缺少依赖时，公开结果能确认 Worker 非零退出，F4 明细只能读到 PID 和退出码，缺少阶段及异常原因。

S1 的监督端在 stderr 投影脱敏诊断。filing-fetch 的公开调用把 ET 的整个 stderr 解成一条用量 JSON。失败诊断与机器收据混用同一输出后，真实调用方无法读取收据，仓内旧 hard-exit 工具也以同一原因失败。独立复验还发现，下载成功后若仅临时目录回收失败，原 stderr 告警同样会让 filing-fetch 把已知用量误报未知。

## 变更与接口

- 在 Worker 原异常捕获边界内加载 provider 依赖，使用既有诊断结构记录 bootstrap 阶段、异常类型、帧和因果链。Supervisor 继续按原路径冷读该结构并交给 F4。
- 机器入口带 --report-usage 时，Worker 监督诊断从原 F4 明细查询，stderr 保持一条用量 JSON。未开此参数时仍有普通控制台诊断。stdout、用量 schema、Worker 非零退出状态、超时和费用语义保持兼容。
- 集中处理 Worker 完成后的临时目录清理。回收失败保留阶段、异常类型和 errno，未确认退出时保留现场及相应阶段。证据写入同一个 F4 明细。清理问题不改变成功资料、已测用量或原失败原因，普通入口仍给出原诊断标识及结构信息。
- 保留 S1 的原始 Worker stderr 禁落盘。子进程本身非零退出时仍按原合同报告 usage_complete=false、usage=null。F4 查询原证据，禁止据费用未知自动重跑。仓内旧验收工具及 filing-fetch 消费者均无需适配。

## 验证与恢复

1. 从干净 0f3b690 的源码夹具复现 3 项失败。真实 Worker 缺 requests 或 bs4 的两案都能冷读终态，但 bootstrap 阶段为空。既有普通非零退出案因 stderr 诊断混入用量 JSON 而失败。
2. 分隔日志通道之前，新增测试的两个机器案均无法对整条 stderr 解 JSON。分隔后两种依赖缺失保留既有结果及整条 stderr 的用量 JSON；不用 --report-usage 的普通入口仍可见脱敏类名和阶段。
3. 本机用 1 次假提供方响应写出 1024 字节，再注入回收 PermissionError。改前机器收据混流，普通输出含原异常文本及路径。改后业务状态仍为 fetched，机器收据保留 1 次请求和 1024 字节，F4 新进程能读出 remove_workdir、PermissionError 和 errno 13。普通输出保留错误类型与阶段，合成私密路径和异常原文均未出现。试验解除模拟失败后回收其目录。
4. 26 项定向离线测试通过，覆盖引导和清理失败、独立进程 F4 冷读和 reconcile、原非零退出与超时、协议隔离、响应限额及 S1 脱敏。Ruff 和 Git diff --check 通过。
5. 测试以请求环境钩子阻止连接、DNS 和发送，故障只含合成标记。每案仅一次真实导入尝试，工作临时目录为空。两次观察冷读一致，owner reconcile 保持 failed、cost_unknown 和原 evidence_ref，未建立新动作库。无真实下载或付费。

## 证据边界与交接

Worker 记录器可用前的进程失败仍只能保留已观察到的退出事实。历史运行里未留存的异常内容无法回补。

filing-fetch 侧独立审查通过。审查者核对四个冻结源码和测试文件，实际把 ET CLI 输出交给 filing-fetch 现有用量解析器。正常成功和模拟拒绝清理都保留已知 1 次请求与 1024 字节，Worker 非零退出只返回一条未知用量回执。模拟未确认退出时没有回收目录或第二次启动，原 F4 详情保留清理阶段。独审最后增量两项通过，与上文 26 项组合覆盖有交集。
