## 已修复

- 在 Worker 导入入口之前或写诊断失败时，父进程从既有子进程的管道读取 Python 已知异常类别和原生故障标记。持续排空管道，不持久化 stderr 原字节。完整结构仍优先从 `worker_error.json` 读取。启动前故障能冷读异常类别和退出码，阶段不明时保留空值。Worker 预检提前返回时保留拒绝原因。
- `transcript_tool --report-usage` 保留 stderr 的原生用量 JSON 和 stdout 的既有响应。未观测到的费用继续按未知处理。子进程仅修改自己的环境副本，父进程的运行号可用于关联本地日志与 F4。
- 本仓现有状态根下的 `logs/runtime_errors.log` 按 2 MiB 轮转，保留两份归档。Worker 故障、CLI 参数拒绝、manifest 发布失败和侧车诊断无法落盘使用简短结构化记录。普通 scraper 侧车拒写会提示一行脱敏告警。两个存储目标都不可写时，结果和费用协议仍按原语义返回。
- 批次 manifest 复用本仓原子替换，保留原编码和换行。写失败后保留已下载原文，并在批次总结和 F4 表明 `manifest_write_failed`，退出码为 1。收据单独写失败的旧复用行为仍受回归测试。
- 原子旁路此前已重抛 `KeyboardInterrupt`。改用 `finally` 清理临时文件，回归验证中断仍抛出、上次结果仍可读。Windows 风格路径和带连字符的文件保留 basename，冻结的 importlib 帧保留虚拟文件名。
- 独审补出的同身份并发问题来自构造 recorder 时提前冻结公用投递。此时同身份的另一个进程可能只写了开始或部分终态。现在打开 recorder 仍恢复和持久化本仓 journal，首个正常结束的进程才确认公用投递。原有 `--capabilities` 冷恢复入口明确补投已有 journal，强停后不重新启动 Worker、不修改已知费用。
- 新增单作业 CI，以 Python 3.10 验证 ET 自有的快速协议测试。通过合成输入验收命令入口、机器用量流、软失败和本地日志。主线程首次发布后核对实际远端运行。

基线新增复现 5 项失败、1 项中断正控通过。在 Windows Python 3.13 获得 97 项定向回归通过，最终入口差量 11 项通过，Python 3.10 语法检查通过。Worker 导入与写障碍测试屏蔽连接、DNS 和发送；实际 HTTP、音频处理和 LLM 调用均为零。
