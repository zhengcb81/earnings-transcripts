# S1-04 Provider 与 Worker 日志脱敏复验

## 问题与根因

2026-11-24 的发布版 `cda3afb` 给 provider 兜底错误加了带 `exc_info` 的日志，异常末行会输出原消息。supervisor 把原始 worker stderr 写进临时具名文件，再用有限正则替换。双词 Bearer、引号内键值、任意消息与真实私有路径没有统一边界。一个进程被强停时，具名原始文件也可能留下。

本轮用纯离线测试替身生成异常，分别覆盖查询凭据、Bearer、引号和请求头、Cookie、任意正文。未读取、传输或保存真实凭据。

## 改动与保留事实

- `retrieval_diagnostics.py` 统一生成异常类型、显式因果或隐式上文、文件名、函数及行号。日志关联用稳定请求摘要。原消息、源码行、完整路径、查询、请求头和 stderr 文本不进入诊断。
- Worker 在本仓既有 `worker_error.json` 保存同一结构。四个 provider 兜底路径包括名单查询，已捕获的业务失败也会经过同一机制，进程退出 0 与 provider 失败可以并存。supervisor 校验已知阶段和结构字段，再沿既有 F4 明细输出。`worker_stderr_type` 留作旧消费方的兼容字段，类型取自结构化诊断。
- 子进程 stdout、stderr 沿用父进程隔离，取消具名原始 stderr。原业务 result、计量、退出码、预算和 F4 观察结构保持兼容。若 worker 在写结构化记录前强停，仍按当前恢复规则保留原退出与用量未知。日志无法补回从未落盘的未处理消息。

## 验证

- 隔离的 `cda3afb` Git 归档执行 `pytest tests/test_s1_provider_error_logging.py`，最终测试形态 4 红。两个 provider 入口暴露原消息或遗漏记录，两个实际 worker 场景可见具名原始文件。
- 候选执行同四个用例、`tests/test_retrieval_runtime.py` 及 `tests/test_f4_batch_replay.py` 的首次失败冷查和已开始预算截止，共 20 绿。实际 worker 覆盖退出 0 且用量 1、硬退 17 且用量未知。对照确认日志含类型与因果，原始出错内容未出现，工作目录回收。
- 仅使用离线替代会话，复验新增供应商调用和费用均为零。另有本仓根目录三个审计 PWF 文件属于并行计划，本次只更新此处及本仓 F4 指针。


## 独立审查

最终源码由两名未参与实现的 agent 核对。第一名复跑四个离线用例。第二名用外部网络禁用的独立 worker 驱动，实测 HTTP 500、已捕获异常与退出 19，业务码、原计量、类型链和源代码位置都相符。没有原始 stderr 文件、真实供应商调用或真实状态写入。两个复验根均已清理。

引导边界也已独立验证。若 worker 在捕获模块加载之前就硬失败，例如被替换的启动脚本在引导阶段直接抛出异常，父进程只保留实际 PID、退出码和失败状态，异常类型及阶段缺证。原始 stderr 不落盘，避免重新引入本次泄露。
